# 工作流

## 1. 一个任务合同包含什么

每个交给成员的任务都必须写清（模板见 [../assets/WORK_PACKAGE.md](../assets/WORK_PACKAGE.md)）：

- **目标**：要改变什么可观察的状态；
- **验收标准**：怎样算完成，最好可自动判定；
- **上下文**：执行者需要知道的最小事实（相关文件、既有约定、已知坑）；
- **读写边界**：可写路径清单，以及明确只读的部分；
- **依赖**：必须先完成的任务或必须先取得的信息；
- **负责人**：恰好一个；
- **不在范围内**：明确写出容易越界的那几项。

验收标准模糊是返工的第一来源：宁可先花时间把标准写清，也不要事后争论“算不算完成”。

## 2. 调度

- **先复用在位成员**：有兼容且空闲的成员时，先给它任务，不要为了并行而新建。
- **并行只在满足三条时使用**：(a) 任务可独立验收；(b) 写作用域不冲突，或彼此隔离；
  (c) 确实存在可并行的独立工作，而不是把一件事切碎制造并行度。
- **一个成员同一时刻只有一个活动任务**；完成后退回空闲并保留其上下文，不要完成即销毁。
- **尊重上限**：并发与成员总数受宿主容量和用户设定约束；到达上限时任务保持等待，
  不要排队塞给忙碌成员，也不要假装还有容量。
- **不虚构状态**：不要声称存在后台常驻、会话持久化或长时监控，除非宿主确实提供且确实发生了。

## 3. 独立审查

- 审查由**未参与实现**的角色执行，输入是改动本身、任务合同与可复现证据。
- 独立性的来源是**第二个执行者**，不是并行：不同执行者串行完成同样算独立审查；
  “顺序执行”本身不降低独立性。
- **没有第二个执行者时不存在独立审查**：只有一个执行者时，只能做**单执行者自检**。
  此时必须如实标注，不得把自检称为独立审查，也不得把同一执行者扮演的不同角色描述成
  相互独立验收。
- 简单任务不进入团队流程，也就不进入本节：直接执行即可，不要声称做过独立审查。
- 审查范围与改动规模相称：小改动做聚焦审查，不要为了形式跑一遍全量。
- 审查结论只有两种有效形态：**可复现的问题**（含定位与复现方式）或**明确的通过**
  （含已覆盖与未覆盖的说明）。不要用“看起来没问题”结案。

## 4. 失败返回修复

- 验证或审查失败时，原任务带证据回到实现者；如需换人，由协调者显式改派。
- 修复后必须**重新验证**；修复者不得自己宣告审查通过。
- 不得由审查者直接改代码来消除失败，也不得降低验收标准来让结果通过。
- 同一个阻塞原因反复出现时（例如基础设施不可用），停止并上报，不要反复重试换参数。

## 5. 证据与最终验收

- 证据是能被第三方按记录复现的东西：命令、退出码、输出片段、文件差异、运行结果。
  只给结论不算证据。
- 记录关键决策与理由，使后来者知道“为什么这样做”，而不只是“做了什么”。
- **最终验收由协调者执行**：逐条对照验收标准，确认证据覆盖了每一条，
  并明确列出**未验证项与残余风险**。
- 不要宣称未验证的内容已经通过；不要把“结构检查通过”当成“行为验证通过”。

## 6. 交付说明

交付时必须包含：

- 实际改动的路径（而不是计划改动的路径）；
- 实际执行的验证及结果；
- 未验证部分与已知风险；
- 角色独立性的实际强度（是否真的由不同执行者完成）。
